# 网关承担协议收敛的语义转换

当前实现只做同协议透传；用户在2026-11-12的访谈中明确要求“需要跨协议语义转换”，以对外大模型协议收敛作为首期真实业务目标。选择由网关承担对外协议与上游协议之间请求、工具调用、响应及SSE事件的语义转换，不将上游协议适配责任继续留给调用方。

这会建立调用方依赖的公共语义契约，区别于仅统一域名、认证和路由；未来移除转换会产生兼容成本。此决定只接受责任边界，不表示已确定协议集合、供应商名单、内部表示、不可映射能力策略或已完成实现；上述内容须继续访谈并落实到设计与验收。

## 后续范围确认（2026-11-12）

用户进一步确认，首期现有三种对外入口Chat Completions、Responses、Messages全部支持跨协议转换，不采用Chat-only转换、另外两种仅透传的首期方案。初次接受责任边界时未确定的协议集合已有上述补充；上游供应商/协议集合、语义能力矩阵和不可表达能力处理策略仍待确认，不在此推定实现或验收已完成。

后续Q6确认首期实际供应商为DeepSeek。其原生兼容入口的可用性不改变网关承担语义转换的责任；具体模型、映射能力和不可表达能力策略仍待确定，未完成实现或验收。

后续Q8确认首期固定模型为deepseek-flash；该决定不减少三种对外入口，也不意味着思考、图片等能力范围或新的付费调用预算已被批准。

后续Q9确认首期能力合同同时纳入思考模式和图片输入，以及文本/多轮、客户端工具调用及结果、SSE与usage；不采用先排除思考和图片的较小首期方案。具体映射、不可表达能力清单与真实业务负载仍待设计和验收。

后续Q12明确首期三个对外入口统一适配到DeepSeek Chat Completions上游，不采用首期完整3×3上游组合。Responses/Messages对外请求及对应响应/SSE仍必须由网关转换，不以供应商原生兼容入口代替；其他上游协议留待后续扩展。
