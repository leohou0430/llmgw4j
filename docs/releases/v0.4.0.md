# llmgw4j v0.4.0

发布日期：2026-11-17（Asia/Shanghai）。

v0.4.0将四阶段能力建设与全盘审查修复发布为单进程Java + SQLite网关。JDK 25、两套JVM数据面（WebFlux/VT）与原生命名SPI继续保留。

## 新增与修复

- `/control/`账号、会话、CSRF、分级角色与真实租户/项目范围；组织、账号、项目/key额度、Key生命周期、供应商凭据、路由、目录、用量和审计形成操作闭环。
- 控制面与数据面共用同一个ExtensionContext实例图。SQLite是密钥、累计token账本、已发布路由与资源目录的唯一权威，业务和审计同事务提交；提交成功后才激活真实路由，支持乐观版本与追加式回滚。
- 项目总额度与key子上限原子预留，权威输入/输出usage结算，未知结果跨重启保守占额；管理员给出原因并核实后核对，禁止清除在途。吊销拒绝新请求，已在途请求继续结算。
- 文件/批任务生命周期与项目目录接通，列表与分页可用；同项目多key共享、跨项目拒绝，创建来源固定并按需加密。修复分页高水位复用、强杀暂存残留、WAL空间漏计、事件循环阻塞管理、登录限速与会话刷新恢复。
- 受控协议转换、工具调用/思考续接、JDK Flow/Future传输、SSE单行边界/EOF/心跳/超时与取消加固；路由改版隔离缓存，缓存旁路头大小写归一。
- 中英文说明、OpenAPI、发布脚本、Docker启动路径和版本统一更新。自v0.3.1以来的详细改动见[CHANGELOG](../../CHANGELOG.md)。

## 升级步骤与兼容变化

1. 停止旧实例写流量，使用SQLite一致性备份保存数据库，保留旧JSON密钥源及原产物；根密钥单独备份。不要复制仍在写入的主库作为完整备份。
2. 为本实例设置持久且独占的`LLMGW_CONTROL_DB`；数据库自动迁移至V9。数据目录应同时容纳WAL/SHM。为每实例独占`llmgw.spool-directory`，不能让多个网关共享本库或暂存路径。
3. 新库首次启动仅导入一次旧JSON和配置Key，旧明文/摘要格式按原`gateway.auth.hash-keys-at-rest`设置识别，导入SQLite后一律摘要存储。之后Key变更通过控制面完成，重启不会恢复已吊销凭据。
4. 首次外部设置`LLMGW_ADMIN_USERNAME`、`LLMGW_ADMIN_PASSWORD`；凭据和带认证的来源快照需要Base64 AES根密钥`LLMGW_ROOT_KEY`。HTTPS使用`gateway.control-cookie-secure=true`，禁止公开管理入口。
5. 完整和只读legacy token都为空时仍是旧`/admin`本地演示开放例外。生产校验要求非空`LLMGW_ADMIN_TOKEN`；配置legacy凭据后默认disabled，迁移必须显式`gateway.admin-token-mode=migration`并限制来源网络。新`/control`使用会话和CSRF，不使用旧token授权。
6. SQLite发布路由为权威，首次之后的启动route配置不会覆盖已发布版本。通过平台管理员`/control/routes/publish`及`rollback`更新，`expectedVersion`冲突409。凭据用`secretId`引用，不能发布明文apiKey；生产限制目标网络策略。
7. 保持`gateway.governance.snapshot-auto-restore=false`。旧`/admin/routes/reload`和`/admin/snapshot/load`对权威状态返回409；JSON可导出观测，不能替换累计账本。新项目token额度默认0，先设置项目总额，再创建/使用key。

若需回退，停止新实例并恢复成对的旧产物和备份数据库；不要让旧版本直接写已经迁移的新库。旧无scope或无目录归属资源不会自动授权给新项目。

## 资产与运行

Release工作流从本tag构建默认JVM JAR、Redis JAR、文档归档、Linux amd64 WebFlux native及`SHA256SUMS`。默认JAR支持`--spring.profiles.active=webflux`或`vt`。native必须按引擎与平台构建；不要将本机验证用的Darwin/VT快速构建视作Linux发行资产。

```sh
java -jar llmgw-app-0.4.0.jar --spring.profiles.active=webflux
# Redis变体仍需 gateway.redis.enabled=true 与 Redis连接参数
sha256sum -c SHA256SUMS
```

发布使用已验证的tag工作流产物；以Release实际附件和校验和为准，不重新命名旧v0.3.1二进制充当新版本。

## 验证与限制

审查冻结源码的完整证据见[16项修复验证](../reviews/2026-11-16-remediation/README.md)：默认1090项（26项Redis条件跳过），独立Redis1089项无跳过，可选profile1090项；双引擎控制面、JWT与SDK及native行为通过。一次流式执行器900秒总时限和最后200请求加权补验如实保留。版本元数据更新后的构建与HTTP验证另见[本次发布记录](v0.4.0-verification.md)，远端工作流以GitHub Actions实际结果为准。

2CPU/2GiB单进程四路64MiB上传场景的容器内存峰值约804/667MiB，无OOM；不作为新tag的通用吞吐A/B或生产SLO。历史性能与真实供应商证据保持原产物归属。本轮未访问付费供应商，未验证远端OTLP收集器。

当前不支持多网关副本共享SQLite、财务级硬预算、企业OIDC/JWKS/SSO或完整代理/WAF功能。Redis提供可选治理，不替换本实例SQLite权威。完整部署与操作见[控制面说明](../control-plane-operations.md)、[安全策略](../../SECURITY.md)和[配置](../CONFIGURATION.md)。
