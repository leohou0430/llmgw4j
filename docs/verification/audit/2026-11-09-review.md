# llmgw4j 全盘审查

审查日期：2026-11-09。基线：`9048f6172d703078de758f80d53af0aff08e988a`。

项目用途：Java LLM 网关，共享治理层，提供 WebFlux 和虚拟线程数据面，另附配对性能实验。按参考实现、团队内部生产、公开开源产品三种标准同时评估；生产负载假设为多调用方、并发请求、长 SSE、可重启及可选多副本。

结论：参考实现有明确价值，模块依赖方向和性能实验口径已有基础。但当前存在可复现的跨租户访问、密钥吊销失效与恢复错误，不能视为已满足本次确认的生产标准。优先修复隔离、密钥生命周期和金额状态，再扩大协议范围。

## 已确认的验收标准

1. 演示与生产模式区分；生产危险配置拒绝启动。
2. 金额预算必须有可靠费用上界，未知价格或不可控费用拒绝准入。
3. 双引擎长期正式支持，契约对等作为发布门槛。
4. 租户默认隔离，资源归属独立于可轮换的 token；共享必须显式配置。
5. 强制治理不可用时拒绝请求，优化能力允许降级；故障放行不可缓存为审核通过。
6. 上游可能已受理且无有效幂等保证时，不自动重试或跨上游 fallback。
7. 硬预算跨重启、多副本保持一致；结果未知的请求保守保留预留并支持对账。

## 必须修复

### 1. [P1] 语义缓存跨租户、模型、协议返回数据（HTTP 已复现）

- **职责**：精确缓存缺失后，通过向量相似度复用响应。
- **问题**：`DefaultGovernanceChain.java:359` 的精确键含 keyId，但 `:367` 调用全局 `findSimilar`，再直接读取返回键，未限制租户、协议、模型或请求参数。A 的 Chat 响应可被作为 B 的 Responses 响应返回。
- **修复**：在检索前限定租户、协议、有效模型/路由及影响响应的参数分区；只在分区内部比较可替代文本。修复前生产关闭语义命中。
- **不修复的影响**：跨租户信息泄露、协议响应不兼容、工具和采样参数失效。精确缓存正确不能抵消此问题。

位置：`llmgw-governance/llmgw-governance-default/src/main/java/io/github/leohou0430/llmgw/governance/inmemory/DefaultGovernanceChain.java:354`；`InMemoryVectorStore.java:50`。

### 2. [P1] 文件、批任务和视频接口缺少资源归属授权（批任务 HTTP 已复现）

- **职责**：根据资源 ID 找回创建时的上游，读取、删除或取消资源。
- **问题**：两套 `handleStickyFetch` 仅用 taskId 找 route，再调用普通鉴权；共享上游凭据代替了租户授权。B 能取消 A 的任务；列表接口也未做租户资源过滤。
- **修复**：保存 `(tenantId, protocol, resourceId)` 到上游路由的绑定，读取及写操作都验证归属；列表只能返回本租户资源。对缺失归属的资源拒绝访问，不能直接 wildcard 转发。
- **不修复的影响**：知道或枚举 ID 的有效用户可操作其他用户资源；上游 project 级密钥不能提供网关租户隔离。

位置：`llmgw-engine/llmgw-engine-webflux/src/main/java/io/github/leohou0430/llmgw/engine/webflux/WebfluxGatewayController.java:621`；VT 对应 `:450`；`llmgw-core/.../routing/InMemoryTaskRouteSticky.java:29`。

### 3. [P1] 吊销密钥没有吊销轮换窗口中的旧 token（Java 已复现）

- **职责**：轮换时让旧 token 短暂兼容；吊销时终止身份访问。
- **问题**：`revoke` 只删除当前 `byToken` 与索引，不清理该身份的 `legacyTokens`、`legacyUntil` 或全部持久化历史 token。`find` 继续接受旧 token。
- **修复**：以稳定身份统一吊销当前和历史 token，并持久化吊销状态；已吊销状态优先于轮换兼容。
- **不修复的影响**：紧急吊销返回成功后，泄漏的旧 token 仍可调用付费上游。

位置：`llmgw-governance/llmgw-governance-default/src/main/java/io/github/leohou0430/llmgw/governance/inmemory/ManagedApiKeyRegistry.java:122`。

### 4. [P1] 重启会重新启用已经失效的轮换旧 token（Java 已复现）

- **职责**：从 key store 恢复运行时密钥与轮换兼容窗口。
- **问题**：构造器把每条持久化记录都放入 `byToken`，包括已有 `rotatedTo` 的旧记录；`find` 首先返回直接命中，绕过 `legacyUntil`。零重叠轮换后，旧 token 重启前无效、重启后有效。
- **修复**：恢复时区分当前和历史凭据，历史 token 只能走受期限及吊销状态约束的兼容路径。
- **不修复的影响**：部署或意外重启使本应失效的泄漏凭据重新生效。

位置：`ManagedApiKeyRegistry.java:57`、`:143`，完整模块路径同第 3 项。

### 5. [P1] 重启后新建密钥复用已有 ID（Java 已复现）

- **职责**：为运行时创建的密钥分配用于用量、预算和管理的稳定 ID。
- **问题**：序号每次从零开始，恢复数据未推进序号；重启前后的第一次创建均产生 `key-1`。两个有效 token 绑定同一 ID，管理索引被覆盖。
- **修复**：使用持久化唯一 ID 或随机唯一 ID，并在恢复与创建时强制身份唯一性。
- **不修复的影响**：不同用户共享账本和限流桶；吊销、轮换可能操作错误凭据。

位置：`ManagedApiKeyRegistry.java:39`、`:84`。

### 6. [P1] 金额预算按估计而非费用上界预留，未知价格按免费处理（源码确认）

- **职责**：在调用付费上游前检查 key 和组金额预算。
- **问题**：`enter` 用输入估计值同时作为输出估计，未约束请求实际输出；`costMicroUsd` 在无价格时返回零。输出远大于输入或模型未建价目时，“硬预算”不能成立；按图片、音频、视频等单位计价也不能仅用 token 公式覆盖。
- **修复**：基于实际计费单位和最大输出建立保守上界，校验实际路由模型与价格；无法证明上界的请求在硬预算模式拒绝。
- **不修复的影响**：短输入长输出、未知模型及非 token 协议可以突破金额承诺。

位置：`DefaultGovernanceChain.java:259`；`llmgw-governance/llmgw-governance-api/src/main/java/io/github/leohou0430/llmgw/governance/QuotaMath.java:53`。

### 7. [P1] 金额账本不持久化，也未由 Redis 实现替换（源码确认）

- **职责**：保存 key 和组的已花费金额与在途预留。
- **问题**：默认 `BudgetLedger` 只有进程内 Map；Redis 自动配置替换 token 配额等组件，却未提供金额账本。重启清零，各副本各持有一份完整预算。
- **修复**：生产硬预算使用可恢复的共享账本，原子管理预留与结算，保留请求标识和未知结果以便对账；未配置时拒绝该模式。
- **不修复的影响**：每次重启或扩容都重新获得额度，组预算也无法限制总花费。

位置：`llmgw-governance/llmgw-governance-default/src/main/java/io/github/leohou0430/llmgw/governance/inmemory/InMemoryBudgetLedger.java:23`；Redis 模块 `RedisGovernanceConfiguration.java:32`。

### 8. [P1] 结算释放与入账不原子，且失败一律按零费用处理（源码交错分析）

- **职责**：把在途预留转为最终花费。
- **问题**：`settle` 先减 reserved 再加 committed；预算 100、原预留 100 时，在两步之间新请求可以再预留 100，随后总占用变为 200。另 `finish` 在流中断、客户端取消等失败时按零金额结算，尽管上游可能已经产生费用。
- **修复**：同一账本状态原子完成释放与入账，结算按请求 ID 幂等；把交付成功与上游已产生费用分开，对未知费用保守保留预留。
- **不修复的影响**：并发结算穿透预算；主动断流或连接丢失造成供应商账单与网关账本偏离。

位置：`InMemoryBudgetLedger.java:49`；`DefaultGovernanceChain.java:421`。原子性问题由具体可达交错得出，未进行真实付费供应商账单实验。

### 9. [P1] 审核服务故障会放行并缓存放行结果（源码确认）

- **职责**：调用外部内容审核服务。
- **问题**：非 200、超时和异常均返回 ALLOW，随后写入 60 秒决策缓存；缺失 action 也默认 ALLOW。缓存键只有文本，而审核请求还携带 model，模型相关策略可被错误复用。
- **修复**：强制审核的故障和不合法响应作为服务不可用处理；缓存只保存有效审核决策，键覆盖策略版本、模型和租户等实际决策维度。
- **不修复的影响**：瞬时审核故障转为持续绕过，策略变更或模型差异不被正确执行。

位置：`llmgw-governance/llmgw-governance-default/src/main/java/io/github/leohou0430/llmgw/governance/inmemory/HttpGuardrail.java:60`。

### 10. [P1] 演示默认配置直接用于对外部署，没有生产启动约束（HTTP、配置确认）

- **职责**：启动网关和管理 API。
- **问题**：空 admin token 直接跳过授权，默认 `sk-demo`，compose 映射 `8080:8080` 且允许 admin 环境变量为空；未发现独立生产模式与危险配置启动校验。无凭据请求 `/admin/routes` 在两引擎均返回 200。
- **修复**：显式区分演示和生产；生产校验管理凭据、示例 key、治理开关以及启用能力依赖，并把安全部署配置作为主入口。
- **不修复的影响**：照默认 compose 部署即可能暴露管理权限，攻击者可修改路由或管理凭据。

位置：`llmgw-app/src/main/java/io/github/leohou0430/llmgw/app/AdminController.java:507`；`docker-compose.yml:10`；`llmgw-app/src/main/resources/application.yml:22`。

### 11. [P1] 自动重试和 fallback 没有表达“上游结果未知”（源码确认）

- **职责**：上游失败时选择下一次尝试。
- **问题**：传输异常和超时默认可重试；即使不可同路由重试，也会转向 fallback。公共策略没有请求提交阶段、协议副作用或有效幂等保证信息。
- **修复**：显式区分未发送、明确拒绝和可能已受理；结果未知的付费操作默认停止，只有已证明安全的尝试才继续。
- **不修复的影响**：超时可能被转化为重复生成和重复收费，异步任务也可能重复创建。具体受影响端点以其是否进入该策略为准。

位置：`llmgw-engine/llmgw-engine-api/src/main/java/io/github/leohou0430/llmgw/engine/ForwardingPolicy.java:133`、`:175`。

### 12. [P1] 密钥持久化写入不原子、无并发保护，失败被吞掉（源码确认）

- **职责**：持久化创建、吊销及轮换结果。
- **问题**：每次操作独立读整文件再覆盖写，没有互斥或原子替换；两次并发创建可各读取同一旧版本，后写覆盖前写。异常仅记录 warn，管理操作仍可返回成功，吊销未落盘时重启会恢复旧状态。
- **修复**：单进程先串行化读改写，并用临时文件和原子替换；多进程使用共享事务存储。安全状态写入失败必须反馈到管理调用，不能报告已持久成功。
- **不修复的影响**：重启丢 key、吊销失效、写入中断留下不可解析文件。

位置：`llmgw-governance/llmgw-governance-default/src/main/java/io/github/leohou0430/llmgw/governance/inmemory/JsonKeyStore.java:65`、`:200`。

### 16. [P2] 外部治理同步调用位于 WebFlux 请求处理路径（源码确认，未做负载定量）

- **职责**：在请求转发前鉴权、审核、检查配额及查询缓存。

- **不修复的影响**：少量慢依赖可占住事件循环，拖慢其他请求并破坏双引擎对照结论的适用性。

### 17. [P2] 响应整体缓冲无独立上限，大文件下载并非流式（源码确认）

- **职责**：转发音频、视频和文件二进制响应。
- **问题**：`fetchRaw` 和 `fetchRawAsync` 使用 `BodyHandlers.ofByteArray`，控制器拿到完整 byte[] 才写下游；请求体 4MB 上限不限制上游响应。多个大文件下载会叠加占用堆。
- **修复**：大二进制响应使用有背压的字节流转发；保留全量缓冲的协议必须设置独立响应大小与并发上限，并明确超限行为。
- **不修复的影响**：正常大视频/文件流量就能产生高堆占用甚至 OOM；不能用小 JSON/SSE 压测证明该路径容量。

位置：`llmgw-app/src/main/java/io/github/leohou0430/llmgw/app/JdkHttpUpstream.java:405`、`:449`；两套 `handleStickyFetch`。

### 18. [P2] 公开产品契约与实际实现存在可核实漂移（文档确认）

- **职责**：向使用者描述支持范围、安全限制及 API。
- **问题**：SECURITY 称 CI 每 PR 执行 verify，实际跳过测试；称上游响应头不透传，但当前已有白名单透传；部署指南称任务粘性仍只有内存，而代码已有 RedisTaskRouteSticky。OpenAPI 仍标记 v12/五协议，却包含后增端点，且未覆盖管理 API。
- **修复**：维护一份经代码和测试验证的能力矩阵，逐项标注演示、单机生产、多副本生产状态；统一版本、安全说明和管理 API 契约。

### 19. [P2] OpenAPI 存在重复操作键，轮询定义挂错路径（解析已验证）

- **职责**：为文档工具和 SDK 生成器提供机器可读接口契约。
- **问题**：`/v1/batches/{id}` 的值为空，批任务轮询 get 被放到 `/v1/files/{id}/content` 下，与该路径已有 get 重复。使用项目现有 SnakeYAML 严格解析，报 `duplicate key get`，行号 502 与 514。
- **修复**：把轮询操作移回批任务路径，并在 CI 使用拒绝重复键的解析器与 OpenAPI 结构校验。
- **不修复的影响**：严格工具拒绝导入；宽松工具可能把文件下载定义覆盖为批任务轮询，生成错误客户端。

位置：`docs/openapi.yaml:474`、`:502`、`:514`。

## 架构与产品判断

- **保留**：共享治理层、独立引擎实现、共享 ForwardingPolicy；模块布局检查已提供可执行约束。没有证据支持推倒重做或新增更多抽象层。
- **优先深化的边界**：租户身份与资源归属、凭据生命周期、预留/结算状态机。这些应由共享层定义不变量，两引擎仅处理传输差异。
- **避免按类长短机械拆分**：控制器确实承载多条路径，但当前应先把授权和费用状态集中到可测试的共享契约，再判断哪些代码值得抽出。
- **产品发布范围**：在上述 P1 修复前，明确标注参考实现；禁用或限制尚不满足隔离、费用约束的能力，不能仅以端点数量表示生产支持程度。
- **性能证据**：现有文档区分主矩阵、wire 实验、同批配对及污染数据，这一点值得保留。本轮没有重跑性能矩阵；历史 mock 基准不证明外部治理、大二进制或多副本场景的容量。
