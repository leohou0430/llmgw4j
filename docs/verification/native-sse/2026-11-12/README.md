## 单变量年轻代试验：不采用

GC诊断用官方支持的`-XX:+PrintGC -XX:+VerboseGC`，依据[GraalVM官方内存管理文档](https://www.graalvm.org/latest/reference-manual/native-image/optimizations-and-performance/MemoryManagement/)。首次诊断批次运行中宿主负载短暂越线，脚本保留样本并退出1（gc-probe.log），该批不计正式性能结果。它仅提供Serial GC日志，不能用其时长单独证明延迟原因。

随后young-probe用同一native二进制做三轮交错对照，仅after增加`-Xmn16m`，两边均带相同GC日志。9样本全部通过。默认与16MiB年轻代的p99中位数分别145.3/149.8ms，成功吞吐555.7/548.1每秒，均无收益。整个进程（含启动、预热及正式轮次）的GC次数166/435、单次中位数12.252/6.989ms、总耗时2838.910/4393.001ms；这些累计量不是正式轮次专属数据。缩短单次暂停没有改善SSE尾延迟，不能采纳这一调参。

## 已知边界与判断

- 两种运行时均正确识别2核。native构建使用Serial、JVM使用G1是已证实配置事实，不是根因结论。
- 首批正式第3轮两边均无CPU节流，native该轮p99反而降至142.9ms；现有数据不足以把所有差异归结为配额节流。
- 宿主loadavg只是粗筛，不能排除短时调度、温度/频率、I/O或其他干扰；本轮没有测量其因果，不声称这些就是原因。
- 因差异未在独立批次稳定出现，尚无能稳定判红的根因反馈环，不据猜测改流式转发路径，也不启动G1重编译。
- 短批次受控上游结果不代表真实供应商性能或长期SLO。没有扩大到96并发或长流的新性能结论。
