# 第二阶段 T2.1 切片2 / T2.2 下载：流式下载合同 + JDK 传输

日期：2026-11-14。落点：`llmgw-provider-api`（合同）+ `llmgw-provider-http-jdk`（唯一 JDK 传输）。纯 JDK，无 Spring/Reactor。本文件记录本轮实际测量。

## 交付

- `UpstreamProvider.fetchStream(UpstreamRequest)`：新增 `default Flow.Publisher<ByteBuffer>`（冷、单订阅，与上传字节合同同类型）；默认抛 UnsupportedOperationException，与既有 fetchRaw 默认一致。新增 default 不强制其它 provider 实现（additive，反应堆绿）。
- `JdkHttpUpstream.fetchStream`：真实流式下载实现。
  - 冷：首次 demand 才发起交换（`start()` 惰性），不在调用时发送。
  - `BodyHandlers.ofInputStream()`（BodySubscribers 支撑的流式 handler），按 16KiB 块读取，**绝不整包 byte[]**。
  - 累计字节超 `maxResponseBytes` → 关闭上游 + 抛 IOException（onError）。
  - 状态 ≥300 → 有界读取错误体（≤64KiB）+ 抛 `UpstreamStatusException`（保留 status/retryAfter）。
  - cancel/close/EOF/error 均经 CAS 恰好关闭响应 InputStream 一次（幂等）；传输级 close() 未改动。
  - 复用既有 `sendBlocking`/`build`/`retryAfterMs`；请求超时仍约束交换发起。逐读空闲超时随慢路径切片 T2.8 加固（已注明）。

## seam 集成测试（受控回环上游，计划 T2.2 seam）

`FetchStreamTest`（4 测试，com.sun.net.httpserver 回环，无引擎）：
- streamsBodyInBoundedChunks：64KiB 体 → 总字节一致 + 内容逐字节一致 + **chunk 数 ≥2**（证明非整包）。
- rejectsOversizedResponse：maxResponseBytes=4、体 8 字节 → onError，且累计停在限额附近（不整包缓冲）。
- surfacesUpstreamStatusError：上游 500 → onError(UpstreamStatusException)，status()==500。
- cancelStopsDelivery：request(1) 后 cancel → 不再投递、静默无错误。
