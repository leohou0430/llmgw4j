# T2.3/T2.4 核心：multipart 流式上传协调器（scan + spool + 字节保真回放）

日期：2026-11-15　模块：llmgw-core（纯 JDK，无 Spring/Reactor）　接缝：`MultipartUpload.prepare`

## 目标与定位

引擎上传桥（T2.3 WebFlux / T2.4 VT）此前把客户端 multipart 正文整包读入 heap（`DataBufferUtils.join` / servlet 整包），
再 `ByteStream.ofByteArray` 交给已流式化的传输（T2.2 `JdkHttpUpstream:649` `BodyPublishers.fromPublisher`）。
本切片交付两引擎共用的核心协调器：边扫描边把正文写入有界磁盘 spool，执行 file/multipart/metadata 限额，
暴露表单字段供治理，并以**字节保真**回放流供上游 POST。整包正文不再驻留 heap。
与 T2.5（MultipartScanner）、T2.6（Spool/SpoolManager）同为「先核心可测组件、后引擎桥」的切片序列。

## 实现

`MultipartUpload.prepare(ByteStream.Source client, String boundary, Limits, SpoolManager)`：
1. `spools.create()` 开一个受限 spool（磁盘余量/配额前置校验）。
2. `MultipartScanner.scan(spool.tee(client), boundary, limits)`：tee 每拉一块即写穿到 spool 并转发，
   扫描器计数文件/累计 multipart/收集 metadata 并执行限额；扫描器不关闭 source。
3. inner finally `client.close()`：正文已全量消费入 spool，无论成功/失败都释放客户端 source 恰好一次。
4. 成功 → 返回 `Prepared`（持 spool + Result）；outer finally `if(!ok) spool.close()`：任何扫描/限额/配额失败
   先释放 spool（删文件 + 归还配额）再抛出，调用方仅在成功时持有 spool。

`Prepared`（AutoCloseable）：`fields()/fileCount()/fileBytes()/totalBytes()/trailingFieldAfterFile()` 供治理；
`bodyLength()=spool.size()`；`body()=ByteStream.of(spool.source())` 字节保真回放，回放终态（正常/取消/错误）
经 ByteStream CAS 关闭 source → spool.close 释放；`close()` 供治理拒绝（从未转发正文）路径释放。spool.close CAS 幂等。

## 设计取舍（诚实记录，非缩小目标）

本协调器对每次上传都落盘 spool。子计划 T2.5 提到「仅前置校验依赖后置字段时落盘」的无 spool 快路径，
是性能优化：现有 MultipartScanner 为**拉模式**，须读完整正文才能判定 trailingFieldAfterFile，
且正文须字节保真转发，故 scan-first 的自然实现即 spool-backed。无 spool 快路径需改为喂模式扫描器
（边转发边扫描）或前缀缓冲，属后续优化切片，**本切片不声称已实现快路径**。spool 配额（单传输 66MiB /
总 264MiB / 4 并行）保证落盘有界、安全，2C2G 下 4×64MiB 仍在总配额内。
