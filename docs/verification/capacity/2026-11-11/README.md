# 2026-11-11 网关容量与现有能力审查

本记录对应本轮最初冻结的 transport 修复产物。后续代码及新证据见 [过载拒绝成本审查](../../perf/2026-11-11/overload/README.md)，下面数字不追溯改写为后续产物性能。

本轮范围经确认：2 CPU / 2 GiB、单副本，无既定 QPS/SLO；以可控 mock 探测资源边界，修复已复现问题，另外用双副本和独立 Redis 验证共享治理。没有真实付费供应商验收。变更未发布，v0.3.1 的历史证据不追溯改写。

## 已复现与修复

| 优先级 | 问题与触发条件 | 修复及反馈环 |
|---|---|---|
| P1 | 上游持续发送正文时，`HttpRequest.timeout()` 未终止 SSE/JSON 请求；400ms 预算在 1s 内仍未结束 | 独立整体 deadline 覆盖正文，异步取消 HTTP future、阻塞中断请求线程；async/blocking × SSE/JSON 四项先红后绿 |
| P1 | VT 流式收到大错误体时，`ofLines()` 无界收集，超过响应限制后仍等待 EOF | 非成功状态改为有界字符串 subscriber；1024B 限制收到超量 chunk 后及时失败，另验 429、Retry-After、caller-thread headers 不变 |
| P2 | 流式响应头慢到达时，响应头前等待计入 idle；首部后及时分块仍被中止 | 收到首部重置活动时间，先 reset 后发布 headersArrived；握手探针固定客户端确实收到首部后再发块 |
| P2 | 10,000 个不同文件路径永久留在 URI map，随动态资源 ID 增长 | 最多保存 1024 项；满后解析新 URI 但不保留，已有热点继续命中；不声称为 LRU |

源码：`JdkHttpUpstream`；新增 `TransportCapacityTest`。定时资源属于每个 transport，惰性启动一个 watchdog 线程，取消任务即从队列移除。正常流完成仍不取消 HTTP transport。

红测试过程保留：`transport-red.log`、`idle-handshake-red.log`、`whole-timeout-probe.log`、`json-whole-timeout-probe.log`。初版 idle 探针受首部缓冲时序影响，已添加 flush 和客户端握手；`caps-green-idle-red.log` 的偶然通过不能证明修复。`vt-error-limit-green.log` 和 `idle-both-red.log` 实际为编译失败，不作为红/绿行为证据。

## 容量方法

工具与可复现命令见 [bench/capacity](../../../../bench/capacity/README.md)。基础镜像只提供 JRE，容器中的 JAR 被冻结产物覆盖；cgroup 实际限额和产物摘要单独记录。默认并发上限不放宽；503 容量拒绝与非预期失败分别报告。表内 p95/p99 为成功请求的 HTTP 发送/等待/接收耗时，不含 DNS/建连/blocked，也不是 TTFT。`audit_preflight_ms` 对 SSE 仅为前置处理、对 JSON 为正文就绪时的本机时间残差，不把它当统一的全链路开销。

正常容量批次位于 `bench/results/capacity-2026-11-11/nominal-matrix/`；初批及连接关闭故障定位批次分别保留于 `measurement/` 和 `final-matrix/`，不混算。这两个早期批次的已完成样本分别有 67 / 75 个非预期响应，诊断采样为 EOF/Broken pipe 的 502。它们完整保留为 [初批](initial-probe/matrix.json) / [连接关闭定位批次](connection-close-probe/matrix.json)。固定 mock 策略后的容量表不能证明真实上游连接关闭故障已经消失；未知 POST 提交状态仍不盲目重试。详见 [过程证据说明](evidence-notes.md)。

正常批次共 110 个样本（96 个正式短请求样本、8 个预热、2 个直连对照、4 个长流），共 770,467 个完整成功响应、750,151 个明确容量拒绝，非预期错误 0；每轮成功数与 mock 请求数相等。正式短请求部分为 753,422 成功、750,151 拒绝。全部样本保留，没有删除失败轮后重算本批。

64 VU 修复版的三轮结果：

| 引擎 | 模式 | 成功 RPS 中位数 [范围] | HTTP p95 ms 中位数 | HTTP p99 ms 中位数 | 容量拒绝 |
|---|---|---:|---:|---:|---:|
| webflux | json | 2522.3 [2461.9, 2603.0] | 30.03 | 41.66 | 0 |
| webflux | sse | 566.1 [563.1, 578.2] | 117.35 | 129.32 | 0 |
| vt | json | 2645.9 [2602.8, 2673.2] | 29.01 | 34.10 | 0 |
| vt | sse | 576.4 [573.6, 578.5] | 117.00 | 121.47 | 0 |

8/32/64 VU 修复版均无容量拒绝；96 VU 全部配置出现明确 503，不能作为零拒绝容量点。基线 WebFlux JSON 的 64 VU 共出现 2 个容量拒绝，已保留在完整表中。96 VU 下修复版 WebFlux JSON 成功 RPS 中位数降至 1730.4、p99 增至 224.89ms，说明持续快速拒绝也会消耗 CPU；保留 64 并发闸门，并优先评估客户端退避和拒绝路径成本，不靠放宽闸门换取表面吞吐。

64 VU 的四个模式/引擎组合，修复版成功 RPS 中位数相对基线变化均在约 −0.5%～0% 内，区间重叠；本轮主要收益是资源边界与超时正确性，不能宣称吞吐提升。JSON 的 WebFlux p99 35.63→41.66ms，但逐轮范围重叠；短 SSE 的 WebFlux p99 122.94→129.32ms，因此另做四轮交错复核，不与本批拼接。

定点复核使用同一冻结 JAR、2C2G、64 VU、15s 预热、每轮 15s，四轮正反交错：基线/修复版成功 RPS 中位数 575.2/573.6，p99 123.47/124.63ms，逐轮范围重叠。该批 11 个样本共 73,519 个成功响应，无拒绝、无非预期错误、上游计数一致；未重复观察到主批同等幅度的尾延迟增幅，但也不能据此承诺零性能成本。见 [独立复核数据](webflux-sse-followup/matrix.md)。

每个配置的 32 VU 长流均完成 32 个请求，平均约 30.1～30.3s，未见截断、超时或上游计数丢失；每配置只有 32 个样本，不能据此承诺可靠尾部 SLO。

容器整个生命周期的内存峰值：before/after WebFlux 407.18/429.76 MiB，before/after VT 378.61/370.00 MiB，均无 OOM。峰值包含 JIT/GC、页缓存等影响，不是每请求堆分配；本轮未进行长期 soak、独立 TTFT 或逐 token 间隔测量。

完整 32 个容量点与每轮数据见 [matrix.md](matrix.md) / [matrix.json](matrix.json)，其中保留计数、p95/p99、资源快照、CPU 节流增量、宿主负载和原始文件 SHA256。共享宿主、短预热和本地 mock 限制使这些数据只能作为本配置观察，不是生产最大 QPS 或跨引擎普遍排名。

## 多副本与产品边界

Redis 共享令牌桶、用量预留/结算、缓存、熔断、API key 注册及任务路由绑定；金额预算、路由配置发布和管理请求日志仍为本地能力。共享 token 配额按估算预留、实际 usage 结算，不是严格财务上限。预留缺少租约与崩溃对账，不能以正常结算测试推断进程强杀后会自动恢复所有预留。

文件/批任务先创建再按租户归属访问；全量列表/分页尚未提供租户资源目录，明确返回 501。OpenAI/Anthropic 是已支持协议的透传和 header 方言，不是任意供应商之间的请求/响应语义转换；本地契约测试也不证明供应商新 API 全兼容。

后续大项按依赖推进：先设计带请求 ID、租约/恢复记录和幂等结算的账本协议，再做共享版本化配置与 key CRUD；文件/任务目录与流式大文件单独立项。继续保留基础模块无 Spring/Reactor、显式组装及实例资源隔离，避免将分布式状态塞入静态单例。

后续大项的依赖和验收条件见 [实施建议](../../../plans/2026-11-11-gateway-next.md)。单节点 Redis 重启不等同于 Sentinel/Cluster 切换；本轮未注入时钟偏移、进行中付费请求强杀或长时间运行，也未覆盖公网 TLS/真实供应商。
